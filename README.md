# pgm

Библиотека на Go и консольная утилита для управления миграциями схемы PostgreSQL.
Миграции пишутся на обычном SQL, нумеруются, применяются и откатываются по порядку.
Состояние хранится в самой базе данных.

## Возможности

- применение и откат версионированных SQL-миграций;
- каждая миграция выполняется в транзакции: применяется целиком или не применяется;
- защита от параллельного запуска (advisory-блокировка PostgreSQL);
- контроль целостности: если файл уже применённой миграции изменили, выполнение отклоняется;
- журнал попыток (успешных и неудачных);
- пробный запуск `--dry-run`, вывод в формате JSON, коды возврата для CI;
- миграции можно встроить в исполняемый файл через `embed.FS`.

## Установка

Нужны Go 1.22 или новее и PostgreSQL.

```
go install github.com/inraise/pgm/cmd/pgm@latest   # утилита
go get github.com/inraise/pgm                      # библиотека
```

Проверка: `pgm --version`.

## Быстрый старт (утилита)

1. Запустите PostgreSQL (подождите несколько секунд после запуска):

   ```
   docker run --rm -d --name pgm-demo -e POSTGRES_USER=pgm -e POSTGRES_PASSWORD=pgm \
     -e POSTGRES_DB=demo -p 5433:5432 postgres:16
   ```

2. Задайте строку подключения.
   Linux и macOS: `export PGM_DSN="postgres://pgm:pgm@localhost:5433/demo?sslmode=disable"`.
   Windows (PowerShell): `$env:PGM_DSN="postgres://pgm:pgm@localhost:5433/demo?sslmode=disable"`.

3. Создайте миграцию и откройте файл `migrations/0001_create_users.sql`:

   ```
   pgm create create_users
   ```

   Заполните обе секции:

   ```
   -- +up
   CREATE TABLE users (id serial PRIMARY KEY, name text NOT NULL);

   -- +down
   DROP TABLE users;
   ```

4. Посмотрите план, примените миграцию и проверьте состояние:

   ```
   pgm --dry-run up
   pgm up
   pgm status
   ```

5. Откатите последнюю миграцию (нужно подтверждение `--yes`):

   ```
   pgm down 1 --yes
   ```

Остановить базу: `docker stop pgm-demo`.

## Формат файлов миграций

- Имя файла: `NNNN_name.sql`. `NNNN` - номер версии (не меньше четырёх цифр),
  `name` - строчные латинские буквы и цифры, слова разделяются `_`.
- Нумерация идёт с 1 без пропусков и повторов.
- Секция `-- +up` обязательна и не может быть пустой.
- Секция `-- +down` необязательна. Если её нет, миграцию нельзя откатить.
  Пустая секция `-- +down` считается ошибкой: удалите её или заполните.
- Перед `-- +up` допустимы только пустые строки и комментарии.
- Файлы с другим расширением и вложенные каталоги игнорируются.
- Команды внутри секции выполняются в одной транзакции. Команды, которые
  нельзя выполнять в транзакции (`CREATE INDEX CONCURRENTLY`), не поддерживаются.

Уже применённую миграцию править нельзя: контрольная сумма файла хранится в базе,
и при расхождении выполнение отклоняется (код 3). Изменения схемы оформляйте
новой миграцией.

## Команды

| Команда          | Действие                                      |
| ---------------- | --------------------------------------------- |
| `pgm up`         | применить все ожидающие миграции              |
| `pgm down N`     | откатить последние N миграций (нужен `--yes`) |
| `pgm status`     | показать состояние миграций                   |
| `pgm create имя` | создать файл со следующим номером версии      |

Состояния в `status`: `applied` (применена), `pending` (ожидает), `changed`
(применена, но файл изменили), `missing` (запись есть в базе, файла нет).

## Флаги

| Флаг                 | Значение                                                           |
| -------------------- | ------------------------------------------------------------------ |
| `--dsn строка`       | строка подключения (или переменная `PGM_DSN`)                      |
| `--dir путь`         | каталог миграций (по умолчанию `./migrations`)                     |
| `--dry-run`          | показать план для `up` или `down`, ничего не выполняя              |
| `--yes`              | подтвердить откат                                                  |
| `--lock-timeout сек` | сколько ждать блокировку (по умолчанию 30)                         |
| `--quiet`            | выводить только ошибки (отчёты `status` и `--dry-run` сохраняются) |
| `--verbose`          | подробная диагностика в stderr                                     |
| `--json`             | вывод в формате JSON                                               |
| `--version`          | показать версию                                                    |

Флаги можно ставить и до команды, и после неё. Результаты выводятся в stdout,
ошибки и диагностика `--verbose` в stderr. Флаги `--quiet` и `--verbose` вместе
использовать нельзя.

## Коды возврата

| Код | Значение                                                       |
| --- | -------------------------------------------------------------- |
| 0   | успешно                                                        |
| 1   | ошибка выполнения (SQL, соединение с базой)                    |
| 2   | ошибка аргументов, конфигурации или файлов миграций            |
| 3   | расхождение контрольной суммы (файл изменили после применения) |
| 4   | не удалось получить блокировку за отведённое время             |

## Права доступа

Строку подключения лучше передавать через переменную окружения `PGM_DSN`, а не
флагом: флаги видны в списке процессов.

Для применения миграций создайте отдельную роль, а не используйте суперпользователя,
и дайте ей права на схему. Роль должна владеть изменяемыми объектами или иметь на них права:

```sql
CREATE ROLE pgm_migrator LOGIN PASSWORD '...';
GRANT CONNECT ON DATABASE app TO pgm_migrator;
GRANT USAGE, CREATE ON SCHEMA public TO pgm_migrator;
```

Команда `status` ничего не меняет и не берёт блокировку, поэтому работает под ролью
только для чтения:

```sql
CREATE ROLE pgm_reader LOGIN PASSWORD '...';
GRANT CONNECT ON DATABASE app TO pgm_reader;
GRANT USAGE ON SCHEMA public TO pgm_reader;
ALTER DEFAULT PRIVILEGES FOR ROLE pgm_migrator IN SCHEMA public
  GRANT SELECT ON TABLES TO pgm_reader;
```

## Использование как библиотеки

```go
//go:embed migrations/*.sql
var migrationsFS embed.FS

db, err := sql.Open("pgx", dsn) // драйвер выбираете вы
if err != nil {
	return err
}
m, err := pgm.New(db, migrationsFS, "migrations")
if err != nil {
	return err // набор миграций некорректен: проверяется до обращения к базе
}
if err := m.Up(ctx); err != nil {
	return err
}
```

Ошибки проверяются через `errors.Is`: `pgm.ErrChecksumMismatch`, `pgm.ErrLockTimeout`,
`pgm.ErrInvalidSet` и другие. Ошибка выполнения миграции имеет тип `*pgm.MigrationError`.
Полная справка: `go doc -all github.com/inraise/pgm`.

## Как это работает

- В базе создаются две служебные таблицы: `schema_migrations` (применённые версии,
  контрольные суммы, время) и `schema_migration_log` (журнал попыток со статусами
  `started`, `success`, `failed`).
- Перед изменениями берётся advisory-блокировка на отдельном соединении; второй экземпляр
  ждёт её освобождения не дольше `--lock-timeout`.
- Контрольная сумма считается по содержимому файла без BOM и с переводами строк `\n`,
  поэтому не зависит от редактора и настроек git.
- Ядро зависит от интерфейса хранилища, а не от PostgreSQL: это позволяет тестировать
  его без базы.

## Ограничения

- Только PostgreSQL.
- Нет генерации миграций из моделей и графического интерфейса.

## Разработка

```
docker compose up -d
export PGM_TEST_DSN="postgres://pgm:pgm@localhost:5433/pgm_test?sslmode=disable"
go test ./... -race -cover
```

Без `PGM_TEST_DSN` интеграционные тесты пропускаются. Каждый такой тест создаёт и удаляет
собственную базу данных.
